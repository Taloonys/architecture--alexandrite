# Какие логи будем собирать...
* ID компонента (который работает с запросом или принимает решение по нему, 
включая смену состояния заказа) :: INFO
* Сам факт изменения состояния заказа :: INFO
* ID юзера + ID заказа, т.к. небходимо понимать, кому, в случае чего, восстанавливать заказ :: INFO
* Метки времени - нужны для отслеживания времени выполнения запросов и того, какие запросы встряли :: DEBUG
* Очевидно, ошибки при попытке модифицировать состояние заказа или принятия запроса в сервис ("выхлоп" валидаторов) :: ERROR
* Если вопрос трассировки затруднительный, то можно на 70-80% загрузки контейнеров выдавать лог :: WARN
* Не очень понимаю, как это технически реализовать, но попытаться логировать DLQ, если для этого ещё ничего не предпринято :: WARN

# Мотивация
* Из всех инструментариев наблюдаемости системы это самый важный момент, т.к. здесь вполне можно заменить некоторую информацию из трассировки и кое-как критически важные моменты из контекста мониторинг ресурсов
* Логи - основной субъект для аналаза событий системы
* Логирование позволяет завести аллёртинг на критически важные случаи
* Логирование позволяет запротоколировать утерянные заказы и восстановить их человеческими ресурсами

# Предлагаемое решение
* Техстэк: *Grafana Loki & S3 storage + Grafana + Vector*
* Сбор данных с сервисов через агент *Promtail*
* У пользователей API и операторов, будет доступ к UI логам, можно ограничить их через labels filter
* Доступ к БД логов будет только у Админов
* Политика хранения:
    * Логи с сервисов будут храниться около 1-3 месяца (хранилища до 100 Гб), если введены трассировка и т.п. и этого хватает для наблюдаемоти и ловли задержки запросов, то достаточно будет 1 месяца
    * Информация и пользователях 3-5 лет (для отчётности, хранение данных отталкивается от политики soft-delete'а), размерность примерно 1 ТБ
    * Логи под сервисы и под броккер хранятся в разных индексах, сенсатив дата тоже отдельным индексом.
* scheme link -> https://drive.google.com/file/d/1KgPVtfza-LgzMEd8QeTWKn4MyIRRz0Om/view?usp=drive_link

# Краткое сравнение
* Grafana-context как-то полегче в реализации, поддержке и развёртывании
* ELK - требует сложной настройки, не похоже, что системе нужно содержать огромные объёмы логов + дорогое обслуживание
* SigNoz тоже вполне подходит, как вариант, но графану выбрал из-за более низкой стоимости

# Система анализа логов
* 10 запросов с логином с 1 API - блокировать запросы с IP на полтора часа
* Дельта запросов за 1 минуту изменилась на 800 запросов - сигнал в реконфигурирование на Backpressure
* Запросы PRICE_CALCULATED и MANUFACTURING_APPROVED висят больше 40 минут - алёрт операторам
* Превышение загрузки физ.пк с сервисом в 90% - алёрт на ручное масштабирование
