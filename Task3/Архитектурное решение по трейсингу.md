# Необходимые места для трейсинга:
* `Shop API` -> `3d files storage`
* `3d files storage` -> `MES API`
* `MES API` -> `Message Queue`
* `Message Queue` -> `CRM API`

# Мотивация
* Упрощённое исследование инцедентов по типу утери сообщений в брокере
* Полная картина в случае, когда статус не изменился по некоторой внутренней ошибке, и по этому поводу в сервисе нигде нет фидбека
* Команда довольно маленькая, длительный анализ логов парой человек занимает огромное кол-во времени, для логов проще или добавить ИИ, или же облегчить работу трейсингом. QA-инженер, в таком случае, может даже помочь с автоматизацией и точечно выдавать проблемные места сразу, без длительного анализа.

# Компромиссы (ну вообще drawbacks)
На самом деле, это во многих смыслах излишне дорогостоящее решение, некоторые отслеживаемые моменты можно заменить остальными средствами мониторинга системы:
* Например контекст "откуда-куда" можно заменить и квалификаторами или специальными метками в логах, сервисов нынче довольно мало, поэтому это будет не сильной проблемой
* Например длительность запросов, это можно заменить метками времени и подсчётами времени запросов на их основе
* Некоторые случаи утери сообщение можно покрыть доплнительными средствами RabbitMQ, если я правильно понимаю, то некоторую картину в этом смысле дополнит механизм подтверждений, помимо уже предложенной очереди мёртвых сообщений

# Аспекты безопасности
> А, у системы же вообще никакой авторизации нет...
* Внедрение доп. API и инстанса с *Keycloack*, где доступ к трейсингу будет только у операторов, т.е. 
* Можно внедрить дополнительное шифрование запросов в обмене сообщениями внутри системы, но тогда это сильно нагрузит систему, превентивно можно остаться на API Gateway
